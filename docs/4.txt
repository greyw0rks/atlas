# Document 4: CockroachDB Data Architecture

## Project Name

# Atlas

**Version:** MVP 1.0

---

# Purpose

This document defines how Atlas stores, retrieves, updates, and manages persistent memory using CockroachDB Cloud.

CockroachDB is **not simply the application's database**.

It is Atlas's long-term memory.

Every investigation, relationship, entity, and semantic embedding is persisted in CockroachDB, making it the single source of truth for all intelligence generated by the platform.

The schema is designed for:

* horizontal scalability
* high availability
* ACID transactions
* PostgreSQL compatibility
* distributed SQL
* vector search
* future multi-region deployments

---

# Database Design Principles

Every table should follow these principles.

### Single Responsibility

Each table represents one type of knowledge.

Avoid large "catch-all" tables.

---

### Immutable Evidence

Evidence should never be modified.

Corrections create new records linked to the original.

---

### Version Important Knowledge

Summaries, AI conclusions, and risk assessments should support version history.

Never overwrite historical intelligence.

---

### UUID First

Every record uses UUIDs as its primary identifier.

Blockchain addresses are unique business identifiers but not primary keys.

---

### Soft Deletes

Records should never be permanently removed unless explicitly required by an administrator.

Use:

* `deleted_at`
* `is_deleted`

---

### Auditability

Every critical mutation should be traceable.

Store:

* created_at
* updated_at
* created_by
* updated_by
* source

# JSON Usage

JSON columns should only store dynamic data.

Examples

Evidence metadata

```json
{
  "gasUsed": "...",
  "block": "...",
  "token": "...",
  "method": "transfer"
}
```

Avoid storing structured business data inside JSON.

---

# Transactions

Every investigation should execute within transactions where consistency is required.

Example

Investigation completes

↓

Insert investigation

↓

Insert wallets

↓

Insert relationships

↓

Insert evidence

↓

Generate embeddings

↓

Commit

If any critical step fails, the transaction should roll back where appropriate, leaving the database in a consistent state.

---

# Data Retention

Atlas prefers archival over deletion.

Policy

* investigations remain permanent
* evidence remains permanent
* relationships remain permanent
* conversations may expire based on user settings
* audit logs follow configurable retention policies

# Why This Schema Fits Agentic Memory

This schema separates different forms of knowledge while allowing them to be connected through relationships and semantic search.

A single investigation may produce:

* new wallets
* new entities
* new evidence
* new patterns
* updated confidence
* additional relationships
* semantic embeddings

Those become permanent knowledge that every future investigation can reuse.

CockroachDB is therefore more than persistent storage—it is Atlas's distributed memory engine.
