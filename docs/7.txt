# Document 7: Memory Agent

## Project Name

# Atlas

**Version:** MVP 1.0

---

# Purpose

The Memory Agent is the heart of Atlas.

If the Investigation Agent is the detective, the Memory Agent is the institutional memory that ensures nothing valuable is forgotten.

Every investigation, relationship, entity, and conclusion ultimately flows through the Memory Agent before becoming permanent knowledge.

Unlike a traditional database layer that simply saves records, the Memory Agent decides:

* what should be remembered
* what should be updated
* what should be merged
* what should remain unchanged
* what confidence should change
* what relationships should be created
* what embeddings should be regenerated

The Memory Agent transforms raw investigation output into durable intelligence.

---

# Core Philosophy

Atlas should never ask the same question twice if it already knows the answer.

The purpose of the Memory Agent is to ensure that knowledge compounds over time.

Each investigation should increase the intelligence of the entire system.

Memory should become richer, more connected, and more trustworthy after every investigation.

---

# Responsibilities

The Memory Agent is responsible for:

* storing investigations
* updating wallet intelligence
* updating entity intelligence
* managing memory versions
* generating embeddings
* detecting duplicate knowledge
* linking relationships
* maintaining confidence scores
* preserving evidence history
* retrieving relevant memory
* refreshing stale knowledge
* managing memory integrity

The Memory Agent is **the only component allowed to write long-term intelligence into CockroachDB**.

No other AI agent should bypass it.

---

# Inputs

The Memory Agent receives structured outputs from other agents.

Examples include:

* completed investigations
* wallet summaries
* entity summaries
* evidence
* relationship proposals
* pattern detections
* AI conclusions
* semantic summaries

It never receives raw user prompts directly.

---

# Outputs

The Memory Agent produces:

* updated memory records
* new versions
* relationship updates
* semantic embeddings
* confidence adjustments
* duplicate detection reports
* memory retrieval results
* memory integrity reports

---

# Memory Pipeline

Every write follows the same pipeline.

```text
Receive Investigation

↓

Validate Structure

↓

Retrieve Existing Memory

↓

Compare Existing Knowledge

↓

Detect Duplicates

↓

Merge New Evidence

↓

Version Updated Knowledge

↓

Generate Embeddings

↓

Update Graph References

↓

Persist Transaction

↓

Return Memory IDs
```

No memory should skip this pipeline.

---

# Memory Creation

New knowledge is created only when Atlas determines that the information adds value.

Examples:

A previously unknown wallet.

A newly discovered bridge.

A new laundering pattern.

A previously unseen entity.

A newly verified relationship.

If no new knowledge is produced, Atlas should strengthen existing knowledge rather than creating duplicate records.

---

# Memory Updates

Updates should be incremental.

Never overwrite valuable historical information.

Instead:

Current Wallet

↓

New Investigation

↓

Merge

↓

Version

↓

Increase Confidence

↓

Preserve History

Memory should evolve instead of being replaced.

---

# Memory Versioning

Every major intelligence object supports version history.

Versioned objects include:

* wallet summaries
* investigation summaries
* entity descriptions
* pattern descriptions
* AI conclusions

Example

```text
Wallet Summary v1

↓

Wallet Summary v2

↓

Wallet Summary v3
```

Users should be able to inspect previous versions for auditing and explainability.

---

# Duplicate Detection

Before writing memory, Atlas checks whether similar knowledge already exists.

Duplicate detection combines:

* exact matching
* semantic similarity
* relationship overlap
* evidence overlap

Possible outcomes:

## New Knowledge

Create a new record.

---

## Existing Knowledge

Update the existing record.

---

## Similar Knowledge

Merge with review.

---

## Conflicting Knowledge

Preserve both until resolved.

---

# Memory Merging

Merging is one of the most important capabilities of Atlas.

Example

Investigation 1

Wallet funded through Coinbase.

Confidence:

65%

Investigation 2

Wallet funded through Coinbase and later bridged to Base.

Confidence:

92%

Merged Result

Wallet funded through Coinbase before bridging to Base.

Confidence:

94%

Evidence:

Combined

History:

Preserved

Nothing should be lost during a merge.

---

# Confidence Evolution

Confidence is dynamic.

Factors that increase confidence:

* repeated observations
* corroborating evidence
* multiple investigations
* verified relationships
* trusted data sources

Factors that reduce confidence:

* contradictory evidence
* stale information
* failed verification
* disputed attribution

Confidence should evolve naturally as Atlas learns more.

---

# Evidence Preservation

Evidence is immutable.

Memory stores references to evidence rather than modifying the evidence itself.

Example

Wallet Summary

↓

Evidence A

Evidence B

Evidence C

If evidence becomes invalid, Atlas marks it as deprecated rather than deleting it.

---

# Relationship Expansion

Whenever new memory is stored, Atlas checks for possible graph updates.

Example

Wallet A

↓

Funds

↓

Wallet B

Wallet B

↓

Uses

↓

Bridge X

Bridge X

↓

Moves Assets To

↓

Base

The Memory Agent submits these proposed relationships to the Knowledge Graph Agent for validation and insertion.

---

# Embedding Generation

Meaningful semantic changes require new embeddings.

Examples:

* updated wallet summary
* new investigation summary
* revised entity description
* newly identified pattern

Minor metadata changes should not regenerate embeddings.

Embedding generation may run asynchronously if needed.

---

# Memory Retrieval

When another agent requests memory, the Memory Agent combines multiple retrieval strategies.

Order of operations:

1. Exact object lookup
2. Graph relationships
3. Investigation history
4. Pattern memory
5. Semantic similarity
6. User-specific context

Results are merged before being returned.

The requesting agent should never need to know how retrieval works internally.

---

# Memory Freshness

Every memory has a freshness score.

Factors include:

* last verification
* last investigation
* evidence age
* blockchain activity
* confidence

Older memories are not deleted.

Instead, they are flagged for revalidation.

---

# Scheduled Memory Refresh

Background jobs periodically review memory.

Tasks include:

* regenerate embeddings
* verify wallet activity
* update risk scores
* refresh entity summaries
* recalculate confidence
* detect obsolete relationships

This ensures Atlas improves even without direct user interaction.

---

# Conflict Resolution

Conflicting knowledge should never be silently discarded.

Example

Investigation A

Wallet belongs to Exchange X.

Confidence:

72%

Investigation B

Wallet belongs to Bridge Y.

Confidence:

89%

Atlas stores both findings.

The conflict is visible.

Future investigations determine which hypothesis gains confidence.

Truth should emerge through evidence rather than replacement.

---

# Memory Integrity

Before committing changes, the Memory Agent verifies:

* required fields exist
* referenced objects exist
* evidence links are valid
* relationships remain consistent
* semantic embeddings match the latest version
* transactions are complete

Invalid memory must never be written.

# Performance Principles

The Memory Agent should:

* minimize duplicate writes
* batch updates when appropriate
* use transactions for consistency
* avoid unnecessary embedding generation
* cache frequently accessed memory

Performance should never compromise correctness.

---

# Failure Recovery

If memory persistence fails:

* rollback the transaction
* preserve investigation output in temporary storage
* retry according to policy
* log the failure with context
* notify monitoring systems if repeated failures occur

No investigation should be silently lost.
