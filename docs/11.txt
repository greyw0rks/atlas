# Document 11: Wallet Investigation Pipeline

## Project Name

# Atlas

**Version:** MVP 1.0

---

# Purpose

The Wallet Investigation Pipeline defines the complete lifecycle of how Atlas investigates a blockchain wallet.

This is the primary workflow of the platform and represents how all major components cooperate to transform a wallet address into an evidence-backed intelligence report.

The objective is not simply to retrieve blockchain data.

The objective is to answer:

* Who controls this wallet?
* What has this wallet done?
* Who is it connected to?
* Have we seen it before?
* Does its behavior match known patterns?
* How risky is it?
* What should an investigator look at next?

Every completed investigation should also improve Atlas's long-term memory.

---

# Core Philosophy

Every wallet investigation follows the same disciplined process.

Atlas should never:

* jump directly into blockchain queries
* ignore historical memory
* duplicate previous work
* produce unsupported conclusions

Every investigation begins with what Atlas already knows before gathering new intelligence.

---

# Stage 1: Input Validation

Atlas validates:

* wallet format
* blockchain compatibility
* checksum (where applicable)
* supported network

Invalid inputs should fail immediately with a clear explanation.

No external API calls should occur before validation.

---

# Stage 2: Blockchain Identification

Determine:

* blockchain
* address type
* wallet standard
* supported providers

Example:

Ethereum

↓

Use Ethereum investigation strategy.

Bitcoin

↓

Use UTXO investigation strategy.

The investigation pipeline adapts based on blockchain characteristics.

---

# Stage 3: Memory Retrieval

Before contacting external providers, Atlas requests existing knowledge.

Retrieve:

* wallet profile
* previous investigations
* entity associations
* graph relationships
* previous reports
* confidence history

The Investigation Agent should avoid collecting information Atlas already possesses unless it requires revalidation.

---

# Stage 4: Graph Retrieval

The Knowledge Graph Agent expands context.

Examples:

Wallet belongs to:

Exchange

↓

Wallet funded:

Multiple addresses

↓

Wallet connected to:

Known protocol

↓

Wallet appears in:

Previous investigations

This provides valuable context before blockchain analysis begins.

---

# Stage 5: Semantic Retrieval

Atlas searches for similar investigations.

Questions include:

* Have we seen similar behavior?
* Does this resemble known laundering?
* Is this similar to previous phishing campaigns?

Semantic retrieval supplements graph intelligence.

---

# Stage 6: Investigation Planning

The Investigation Agent generates an execution plan.

Example

```text id="kj4a8s"
Objective:

Determine whether this wallet is part of a phishing campaign.

Required Actions:

Retrieve transactions.

↓

Analyze counterparties.

↓

Inspect bridge usage.

↓

Compare against phishing patterns.

↓

Generate conclusions.
```

Planning prevents unnecessary work.

---

# Stage 7: Blockchain Data Collection

Atlas gathers blockchain intelligence.

Examples:

* balances
* token holdings
* transfers
* internal transactions
* smart contract interactions
* NFT activity
* bridge usage
* governance participation
* approvals
* protocol interactions

Every provider is accessed through an abstraction layer.

---

# Stage 8: Wallet Profiling

Atlas builds a behavioral profile.

Example characteristics:

* active chains
* preferred protocols
* transaction frequency
* average transaction value
* active time windows
* contract deployment history
* bridge usage
* token preferences

The profile summarizes behavior rather than listing every transaction.

---

# Stage 9: Counterparty Analysis

Identify significant counterparties.

Examples:

* exchanges
* bridges
* multisigs
* protocols
* treasury wallets
* deployers
* recurring recipients

Counterparties become graph candidates.

---

# Stage 10: Entity Resolution

Atlas determines whether the wallet belongs to a known entity.

Possible outcomes:

Known Exchange

Known Protocol

Known DAO

Known Scam Group

Previously Unknown Entity

If uncertain:

Create a candidate entity rather than forcing attribution.

---

# Stage 11: Pattern Analysis

The Pattern Recognition Agent compares behavior against historical intelligence.

Examples:

Bridge Hopping

Wallet Splitting

Sybil Farming

Wash Trading

MEV

Laundering

New candidate behaviors are recorded for future evaluation.

---

# Stage 12: Relationship Discovery

The Investigation Agent proposes relationships.

Example

```text id="4bgk1r"
Wallet

↓

Funded

↓

Wallet

↓

Uses

↓

Bridge

↓

Interacts With

↓

Protocol

↓

Deposits Into

↓

Exchange
```

These proposals are validated by the Knowledge Graph Agent before becoming permanent intelligence.

---

# Stage 13: Risk Assessment

The Risk Engine evaluates:

* behavioral signals
* graph context
* semantic matches
* historical investigations
* evidence
* pattern matches

Outputs include:

* priority level
* confidence
* explanation

The Risk Engine never determines guilt.

---

# Stage 14: Report Generation

Atlas produces two reports.

---

## Investigator Report

Readable.

Contains:

Executive Summary

Key Findings

Timeline

Evidence

Relationships

Risk Assessment

Recommended Next Steps

Open Questions

---

## Machine Report

Structured.

Contains:

Wallets

Entities

Evidence

Patterns

Relationships

Confidence

Metadata

This report becomes input for the Memory Agent.

---

# Stage 15: Memory Persistence

The Memory Agent receives the structured report.

Tasks include:

* update wallet memory
* update investigations
* merge knowledge
* regenerate embeddings
* preserve evidence
* version summaries

Every investigation improves Atlas.

---

# Stage 16: Graph Update

The Knowledge Graph Agent:

* validates relationships
* inserts new nodes
* updates confidence
* expands graph

The intelligence graph becomes richer after every investigation.

---

# Stage 17: Completion

Atlas returns:

* investigation report
* evidence
* confidence
* graph summary
* related investigations
* suggested follow-up investigations

The investigation becomes available for future semantic retrieval.

If a provider fails:

Retry

↓

Switch Provider

↓

Continue Investigation

↓

Mark Missing Data

↓

Complete If Possible

Investigations should degrade gracefully.

# Investigation Priorities

Atlas supports multiple priorities.

Low

Background refresh.

Medium

Standard user investigation.

High

Critical user request.

Urgent

Security monitoring or active alert.

Priority affects scheduling, not reasoning quality.

# Guiding Principle

A wallet investigation is not a sequence of API calls.

It is a structured reasoning process.

Atlas begins with memory, gathers only the intelligence it needs, validates every conclusion, connects new knowledge to existing knowledge, and ensures that every completed investigation leaves the platform more intelligent than before.
